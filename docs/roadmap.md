# Roadmap

Motion Lab follows a dependency-driven sequence. Each stage must produce evidence and an artifact that the next stage can use. Dates are intentionally omitted until implementation capacity and experimental runtime are known.

## Status vocabulary

- **Planned:** scope and completion criteria are documented, but implementation is not verified.
- **In progress:** work has started, but one or more completion criteria remain unmet.
- **Complete:** committed code and artifacts satisfy the documented gate and the result has been reproduced from a clean checkout.

The first two experiments are **complete**. Later experiments remain
**planned**.

## Stage 1 — Feedback control in MuJoCo

**Goal:** build intuition for closed-loop control by comparing proportional and proportional-derivative controllers on a simple actuated system.

**Questions**

- How does proportional gain affect speed, overshoot, and oscillation?
- How does derivative feedback change damping and settling behavior?
- Which apparent improvements are paid for with greater control effort or sensitivity?

**Published artifact**

- A deterministic MuJoCo experiment with P and PD controllers.
- Saved configurations for a small gain sweep and scenario suite.
- Raw episode metrics and plots generated from those records.

**Completion gate**

- Environment and controller source are committed.
- Dependency versions and commands are documented.
- The same scenario set is used for both controllers.
- Metrics are generated by code rather than transcribed manually.
- Results reproduce from a clean checkout within documented tolerance.

**Status:** Complete. The model, controllers, deterministic runner, declared
gain sweep, visual replay, MP4 exporter, automated checks, and
[multi-scenario evidence](../experiments/01-feedback-control/results/evaluation-v1/report/report.md)
are committed. A separate clean checkout of source commit `7a6d152` passed all
188 tests and regenerated all 18 evidence files byte-for-byte. The evidence is
limited to the declared simulated one-link protocol and retains all four
P-controller failure cases.

## Stage 2 — State-transition trajectories

**Goal:** turn control rollouts into a reliable dataset for prediction.

Each transition will have the conceptual form:

```text
(state_t, action_t, next_state_t)
```

It must also retain timing, episode boundaries, termination reason, environment version, controller configuration, and random seed. These fields prevent a numerically convenient array from becoming an ambiguous scientific artifact.

**Published artifact**

- A versioned transition schema.
- A recorder and validator.
- Training, validation, and test splits separated by episode or scenario rather than shuffled individual rows.
- A small dataset card describing collection policy and coverage.

**Completion gate**

- Schema, shapes, units, coordinate frames, and sampling interval are explicit.
- Replaying recorded actions under the recorded configuration is validated where deterministic replay is supported.
- Split construction prevents adjacent transitions from leaking across partitions.
- Data validation rejects missing, non-finite, or inconsistent records.

**Status:** Complete. The
[schema-v1 dataset and dataset card](../experiments/02-state-transition-dataset/DATASET_CARD.md)
publish 2,540 transitions from eight simulated episodes. Complete scenarios
define the partitions: 940 training rows across both wide-displacement
directions, 800 validation rows from the negative-to-positive narrow scenario,
and 800 test rows from the positive-to-negative narrow scenario. P and PD
episodes and adjacent transitions never cross partitions. All eight saved
applied-action sequences replayed with zero recorded state error at absolute
tolerance `1e-12`. A separate clean worktree at builder commit `e95c7a0` passed
all 229 tests and regenerated the manifest and three JSONL partitions
byte-for-byte. This is deterministic one-link simulation evidence with one
seed, not learned-model performance or physical-hardware evidence.

## Stage 3 — Forward-dynamics baseline

**Goal:** predict the next state using known dynamics or the simulator before training a learned model.

The baseline answers what can already be achieved from an explicit transition function:

```math
\hat{s}_{t+1} = f(s_t, a_t)
```

It also establishes conventions for state error, angular wraparound, integration step, and multi-step rollout evaluation.

**Planned artifact**

- A one-step prediction interface.
- A simulator-backed or analytical predictor.
- One-step and open-loop multi-step evaluation.

**Completion gate**

- Prediction is evaluated on held-out episodes.
- Metrics are reported per state component and in physically meaningful units.
- Multi-step drift is shown as a function of horizon.
- Numerical integration and simulator-query baselines are clearly distinguished.

**Status:** Planned.

## Stage 4 — Learned dynamics

**Goal:** learn a transition model from recorded experience and compare it with the forward-dynamics baseline.

Candidate model families should begin with a small multilayer perceptron or residual predictor before recurrent or probabilistic models are introduced.

**Planned artifact**

- A reproducible training pipeline.
- Dataset normalization derived from training data only.
- Checkpoints tied to data and configuration versions.
- One-step and multi-step comparisons with simple baselines.

**Completion gate**

- Training, validation, and test partitions are scenario-safe.
- Ablations separate model capacity, input history, and loss design.
- Results include variance across declared seeds.
- Failure cases and out-of-distribution scenarios are shown.

**Status:** Planned.

## Stage 5 — Model predictive control

**Goal:** use a dynamics model to choose actions by repeatedly planning, executing the first action, observing the new state, and replanning.

For horizon \(H\), a basic objective is:

```math
\mathbf{a}_{t:t+H-1}^{*}
= \arg\min_{\mathbf{a}_{t:t+H-1}}
\sum_{k=0}^{H-1} c(\hat{s}_{t+k}, a_{t+k})
+ c_T(\hat{s}_{t+H})
```

**Planned artifact**

- A common planner interface for random shooting and at least one stronger optimizer such as the cross-entropy method.
- Receding-horizon control using both baseline and learned dynamics where compatible.
- Task-level evaluation under identical action and compute limits.

**Completion gate**

- Planning budget and wall-clock timing are reported.
- State-prediction quality and closed-loop task quality are evaluated separately.
- Comparisons use the same cost, horizon, constraints, and scenario set.
- Safety and actuator limits are enforced outside the learned model.

**Status:** Planned.

## Stage 6 — Visual and latent prediction

**Goal:** investigate whether the predictable, task-relevant part of future observations can be modeled in a learned representation rather than by reconstructing every pixel.

This stage is **JEPA-inspired**, not a claim to reproduce any specific published system. A conceptual latent-prediction objective is:

```math
z_t = E(o_t), \qquad
\hat{z}_{t+1} = P(z_t, a_t), \qquad
\mathcal{L}_{pred} = d(\hat{z}_{t+1}, \operatorname{sg}(E_{target}(o_{t+1})))
```

where `sg` indicates that the target branch is treated as a fixed target for that update. The exact anti-collapse mechanism, architecture, and temporal context remain research choices.

**Planned artifact**

- Observation and latent encoders with an explicit training contract.
- Pixel-space and latent-space baselines.
- Tests of whether representations retain information required for control.

**Completion gate**

- Representation quality is not judged only by training loss.
- Downstream control or probing evaluates task-relevant information.
- Collapse diagnostics and trivial-prediction baselines are included.
- Pixel and latent methods are compared without implying they optimize identical objectives.

**Status:** Planned.

## Stage 7 — Temporal and hierarchical planning

**Goal:** connect fast motor decisions with slower, more abstract decisions over goals, subgoals, or skills.

The working hypothesis is that different levels should operate at different temporal resolutions:

```text
high level: choose goal or skill          (slow)
middle level: predict skill outcome       (medium)
low level: execute feedback control       (fast)
```

**Planned artifact**

- A temporal abstraction interface with explicit initiation and termination conditions.
- Short-horizon controllers or skills that a higher-level planner can compose.
- Comparisons against a flat planner under matched compute budgets.

**Completion gate**

- Skill boundaries and termination logic are measurable.
- Long-horizon evaluation uses held-out task sequences.
- Flat and hierarchical systems receive comparable information and compute.
- Recovery from a failed subgoal is evaluated, not assumed.

**Status:** Planned.

## Cross-stage review questions

Before advancing, ask:

1. What artifact from the current stage is required by the next?
2. Is the relevant interface—state, action, observation, time, or skill—fully specified?
3. Is there a simple baseline that has not yet been tested?
4. Can every reported number be regenerated from versioned inputs?
5. Which conclusion is supported by evidence, and which remains a hypothesis?
